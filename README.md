The self-hosting launcher is available as [`@digestseo/mcp-gsc`](https://www.npmjs.com/package/@digestseo/mcp-gsc). For new analytics/reporting-only connections, explicitly start in read-only mode:

```bash
GSC_ACCESS_MODE=readonly npx -y @digestseo/mcp-gsc
```

On Windows PowerShell, use `$env:GSC_ACCESS_MODE = 'readonly'` followed by `npx -y @digestseo/mcp-gsc` instead. Supply your own Google OAuth and encryption settings from [SETUP.md](SETUP.md) before starting either command.

The npm launcher starts a loopback-only **Streamable HTTP** Worker on `127.0.0.1` (port `8080` by default); it is not a stdio MCP process. You can run the `npx` command from any directory because the launcher resolves its bundled Worker configuration from the installed package. Clients that launch the package should connect to `http://127.0.0.1:8080/mcp` after supplying the Google OAuth and token-encryption environment variables described in [SETUP.md](SETUP.md). The launcher exits before starting Wrangler if `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, or `TOKEN_ENCRYPTION_KEY` is missing or blank, and it also rejects a nonblank `TOKEN_ENCRYPTION_KEY` unless it is valid base64 that decodes to exactly 32 bytes. Errors identify only the invalid or missing setting, never its secret value, so a broken OAuth session is not started. It keeps secret values in the child process environment and Wrangler loads them through declared local secrets; their values are not copied into Wrangler `--var` command-line arguments. Before the first OAuth sign-in, authorize the exact callback `http://127.0.0.1:8080/google/callback` in Google Cloud (or use the same custom `PORT` you launch with); the launcher prints both URLs at startup.

**Docker/Glama network binding.** The ordinary `npx` launcher stays loopback-only by default (`MCP_GSC_BIND_IP=127.0.0.1`). The Docker image explicitly sets `MCP_GSC_BIND_IP=0.0.0.0` **inside the container**, because Docker port forwarding cannot reach a service bound only to the container's loopback interface. When publishing a Docker port on your computer, prefer `-p 127.0.0.1:8080:8080` to restrict host access; expose it beyond the host only with appropriate HTTPS/OAuth deployment configuration and an authorized Google redirect URI. `MCP_GSC_BIND_IP` accepts only `127.0.0.1` or `0.0.0.0`; do not use all-interface binding for ordinary local npm usage.

Local KV and Durable Object state, including the encrypted Google session, is stored in `~/.mcp-gsc/state` by default instead of inside the versioned npm cache. That keeps the local connection available across package upgrades and ordinary npm cache cleanup. Set `MCP_GSC_STATE_DIR` to use another directory; keep the same `TOKEN_ENCRYPTION_KEY` when reusing existing state because stored refresh tokens are encrypted with that key. The launcher prints the effective state directory at startup. The first release with this stable path may require one Google reconnect because older launcher releases stored local state under the npm package cache.

The launcher's **implicit fallback** remains `GSC_ACCESS_MODE=readwrite` for backward compatibility. The read-only commands above and checked-in self-hosting templates explicitly select `readonly`: Google OAuth then requests only the read-only Search Console scope, and the six mutation tools stay unregistered. Opt into `readwrite` only for workflows that actually require changes to Search Console properties, sitemaps or eligible Indexing API URLs.

For Google OAuth and Cloudflare deployment configuration, follow [SETUP.md](SETUP.md).

### Connect the local launcher

For the current verified quick-connect path, supply the Google OAuth and token-encryption environment variables described in [SETUP.md](SETUP.md), then start the npm launcher using the appropriate read-only command above (or deliberately choose `readwrite` for a privileged workflow).

Then connect your MCP client to the launcher's loopback endpoint:

```
http://127.0.0.1:8080/mcp
```

Self-hosted Cloudflare Worker deployments continue to use `https://<your-worker>.workers.dev/mcp`. The repo does not currently advertise the owner-hosted remote as a quick-connect path because its deployed tool contract is behind the published package.

A self-hostable [Model Context Protocol](https://modelcontextprotocol.io) (MCP) server for **Google Search Console**. Connect it to Claude.ai, Cursor, ChatGPT, or any MCP-compatible client and ask your AI assistant about your site's organic search performance — impressions, clicks, top queries, index status, and sitemap health — straight from your own Google account.

It runs on [Cloudflare Workers](https://workers.cloudflare.com/) and ships with Google OAuth onboarding: connect the server in your client, review the mcp-gsc consent page that identifies the requesting MCP client and permissions, then sign in with Google and grant the requested Google Search Console permissions. No API keys to copy around and no service-account JSON to manage.

## Tools

By default (`GSC_ACCESS_MODE=readwrite`), this server exposes 23 tools. Read-only analytics and reporting tools are marked with MCP's `readOnlyHint`; the write tools below can change Search Console properties, sitemaps, or indexing state. Set `GSC_ACCESS_MODE=readonly` to request only the Search Console read-only scope and expose the 16 tools that do not require either write access or the separate Indexing API scope.

| Tool | Access | What it does |
|---|---|---|
| **`server.capabilities`** | Read | List every tool this server exposes and report local Google credential state. `connected` means a stored refresh credential is present; the response also exposes `auth_status_basis` and `provider_auth_live_verified: false` because this discovery call does not probe Google. A later Google tool call can still require reconnection if the credential expired or was revoked. Takes no arguments. |
| **`sites.list`** | Read | List the Search Console properties the connected Google account can access (`siteUrl`, `permissionLevel`). |
| **`sites.get`** | Read | Retrieve one exact Search Console property and the connected account's permission level for it. |
| **`analytics.query`** | Read | Impressions, clicks, CTR, and average position over a date range, with dimensions, filters, safe pagination, and selectable search type. Pass `dimensions: []` for true site totals; Google's aggregate row may omit `keys`. Search Analytics does not guarantee every data row and can return only top rows, so exhausting local pagination is not proof that the provider dataset is exhaustive. `data_state: "all"` can include fresh preliminary data, while `final` returns only finalized data; responses echo `data_state` plus `preliminary_data_possible`, and date/hour groupings preserve Google's incomplete-data boundary metadata when returned. Search appearance discovery is a two-step workflow: group by `searchAppearance` alone to discover the exact values Google returns for the property, then filter to one returned value in a separate query when grouping by page/query/country/device/date/hour. For `search_type: "discover"` or `"googleNews"`, `position_supported` is `false`; those reports expose clicks, impressions, and CTR but not average position, so returned rows can omit `position`, and query grouping/filtering is unavailable. Search Console's dedicated Generative AI performance reports are not exposed by the current documented Search Analytics API as a dedicated search type or filter selector; `generative_ai_report_isolatable` is therefore `false`. Google now exposes the separate `search_type: "webMultimodal"` API surface; `multimodal_report_isolatable` is `true`, but a missing row is not evidence of zero traffic. |

For regional or cross-device Search Analytics without stitching together separate provider requests, use `dimension_filter_groups: [{ "filterLists": [{ "dimension": "country", "expressions": ["DEU", "AUT", "CHE"] }, { "dimension": "device", "expressions": ["MOBILE", "DESKTOP"] }] }]` with `analytics.query` or `analytics.compare`. Google matches **any** value within each list and **all** selected dimensions, so this example means a DACH searcher country **and** mobile/desktop. The MCP normalizes case, accepts 1-50 exact values per list, and rejects invalid/duplicate values and mixing `filters` with `filterLists` on the same dimension (including across groups). Omitting both filter types retains unfiltered behavior. Lists do not add API calls, alter the normal quota, override property permissions, or make returned rows exhaustive; country is the searcher's location, not a URL locale. Requires Google Search Analytics API support announced November 16, 2026.
| **`insights.page_queries`** / **`insights.query_pages`** | Read | Drill from one exact page to its Search Console queries, or from one exact query to the pages Google surfaced for it, with `row_limit` / `start_row` pagination. `insights.page_queries` accepts `query_contains` to narrow query topics; `insights.query_pages` accepts `page_contains` to narrow URLs. Both accept optional singular `country` (ISO alpha-3 searcher geography, not page language) and `device` (desktop/mobile/tablet), or plural `countries` (1-10 distinct ISO alpha-3) and `devices` (1-3 distinct desktop/mobile/tablet); never mix singular and plural within one dimension. Lists apply Google-side OR within a dimension and AND across dimensions, exact page/query, and optional substring in **one** request. Combined results are not per-country/device attribution, and missing or paginated rows do not imply zero traffic or an exhaustive dataset. Web, image, video and Search results News tab are supported; Discover and the separate Google News report lack query data. |
| **`urls.inspect`** | Read | Google's URL Inspection report for the version of one page currently known in Google's index. It is not a live URL test; mobile-usability output is deprecated. |
| **`urls.inspect_many`** | Read | Inspect Google's indexed versions of up to 10 URLs sequentially in one call while preserving input-order results. `index_status_counts` summarizes indexed, not-indexed and unknown states among successful inspections only; failed requests are separate, and this is not site-wide coverage. Each URL still consumes one Google URL Inspection request and one unit of the server's shared inspection safety budget; this does not run live URL tests. |
| **`sitemaps.list`** / **`sitemaps.get`** | Read | List submitted sitemaps or retrieve one sitemap's details. `lastSubmitted` is when the sitemap was submitted to Search Console; `lastDownloaded` is when Google last downloaded the sitemap. Neither value is the sitemap file's modification/deploy time or a page crawl/indexing timestamp. |
| **`insights.quick_wins`** / **`insights.cannibalization`** / **`insights.content_decay`** | Read | Surface average-position opportunity rows, query/page overlap, and evidence-ranked click declines. Quick wins accepts optional `page_contains` (for example `/de/`), `query_contains` (for example `technical seo`) and `country` (for example `DEU` for searchers in Germany, not German-language pages). They combine as Google-side AND filters before pagination to find geographically and topically relevant opportunities without unrelated rows crowding the source window; filtered results are not property-wide. Quick-win candidates use aggregate Search Console average position, not a stable current rank, and optional `max_ctr` (a 0-1 fraction) limits candidates by observed CTR after Google pagination, without proving an SEO problem. Cannibalization accepts optional `query_contains` (for example `pricing`) and `page_contains` (for example `/de/`), combined as Google-side AND filters before source pagination; query scope retains all returned competing URLs for matching topics, while page scope limits observed shares to those URLs rather than property-wide totals. Candidate totals/shares derive from observed query/page rows rather than true query-level property totals. Content-decay accepts optional case-insensitive `page_contains` and `query_contains` across both Google requests, separately or combined as AND before pagination, to compare topic-specific page traffic (not sitewide totals) without extra API calls; it allows 1-240 days per comparison period to fit Search Console history. Content-decay results compare only pages returned in both periods and do not turn one-sided row absence into zero traffic. |
| **`indexing.list_pages`** / **`analytics.compare`** | Read | Analyze pages receiving Search Console impressions and compare two periods, optionally using the same search type and query/page/country/device/search-appearance filters for both periods. `analytics.compare` compares only dimension keys returned in both period responses and includes `observed_dimension_overlap` counts (each period, common and one-period-only) plus up to three one-period-only observed examples from each period, ranked by their returned impressions. These examples help choose follow-up checks, not prove a new or vanished query/page: absent keys in non-exhaustive Search Analytics responses are **not zero traffic**. It defaults to finalized Search Analytics rows with `data_state=final`, preserving Google's omitted-`dataState` behavior; pass `all` explicitly when recent preliminary-capable rows are desired. Discover (`search_type: "discover"`) and Google News (`"googleNews"`, not Search's News tab) can be compared by `page`, `country`, or `device` when that property has eligible data: average position and its change are `null`, never an inferred ranking, and query dimensions/filters are rejected before contacting Google. Each comparison uses the same bounded Search Analytics request path; switching surface adds no extra calls. `indexing.list_pages` is performance data, not index coverage: a missing URL may still be indexed; use `urls.inspect` / `urls.inspect_many` for URL-level index status. Its returned pages retain observed clicks and impressions when Google omits optional average position (`position: null`, never zero). |
| **`reports.weekly_digest`** | Read | Generate a plain-language seven-day performance report with movers, top pages, and evidence-based next steps. Finalized reports can highlight up to three directly returned zero-click query rows with positive impressions, ranked by observed impressions; this is an up-to-25-row, non-exhaustive sample, not proof of missing or anonymized query performance, and uses no extra API request. Optional `search_type` supports Web (default), Image, Video and the Google Search News tab, consistently applied to every request; Discover and the Google News app are excluded because they do not expose query rows. Non-Web reports explicitly label their search surface and avoid Web-specific content advice. Optional `page_contains` restricts matching URLs (such as `/de/`), `device` selects desktop, mobile or tablet, `query_contains` narrows a topic (such as `technical seo`), and `country` selects a searcher country by ISO 3166-1 alpha-3 code (such as `SVN`; not a page locale). All selected filters combine in one Google-side AND group across totals, queries and pages without adding requests. Topic-filtered reports exclude other and anonymized queries and are not property-wide totals; omit filters for unsegmented reporting. Query movers compare only rows returned in both weekly Search Analytics result sets; a query missing from one bounded response is not treated as zero because Google does not guarantee every data row. |
| **`sites.add`** / **`sites.delete`** | Write | Add or remove a property from the connected account's Search Console site set. `sites.add` returns `ownership_verification_performed: false` because ownership verification is a separate Google Site Verification/Search Console workflow. `sites.delete` removes the property from that account's Search Console site set; it does not delete the website itself. |
| **`sitemaps.submit`** / **`sitemaps.delete`** | Write | Submit or remove a sitemap. |
| **`indexing.status`** | Read | Read Google's latest successful Indexing API `URL_UPDATED` / `URL_DELETED` notification receipts for a previously submitted URL. This is notification metadata only, not index coverage, crawl status, indexing completion, or removal completion. It requires `GSC_ACCESS_MODE=readwrite` because Google's metadata endpoint uses the Indexing API OAuth scope. |
| **`indexing.request`** | Write | Requests indexing through Google's Indexing API. Google currently restricts this API to pages containing `JobPosting` structured data or livestream pages containing `BroadcastEvent` inside `VideoObject`. It is not available for general webpage submission. Google's documented default is 200 publish requests/day/project shared by updates and removals. Eligible content types, API authorization, quota limits and spam policies still apply; this quota is not permission to submit other page types or exceed Google's limits. |
| **`indexing.remove`** | Write | Request a `URL_DELETED` notification for a previously eligible Indexing API page. Before removal, the URL must already return HTTP 404/410 or expose a `noindex` meta directive addressed to `robots` or `googlebot` (not just `googlebot-news`). Google's receipt does not prove removal completed; use URL Inspection for indexed-state evidence. |

For aggregated regional weekly reports, `reports.weekly_digest` also accepts `countries` (1-10 distinct ISO alpha-3 codes) and `devices` (1-3 distinct device values) as arrays. Use the plural alternative instead of `country` or `device` for that dimension; never provide both forms. Values within a list are ORed by Google using `filterLists`; page, query, country, and device scopes remain ANDed across every request. A filtered report describes only the selected searchers, not all site traffic. The five finalized (or three preliminary) Search Analytics requests and existing shared quotas are unchanged. For an exact observed page or query, `insights.page_queries` and `insights.query_pages` preserve those same list scopes in one bounded read; `analytics.query` remains an alternative. Keep exact dates, search surface and filters in follow-ups.

For one exact observed query, use `query: "Technical SEO"` in `reports.weekly_digest` or `gsc-weekly-client-report` instead of `query_contains`. Google applies case-sensitive query equality on every digest request; supplying both selectors is rejected. Keep the exact query and any selected page and searcher filters in `analytics.compare` and `analytics.query` follow-ups, rather than substituting a substring-only helper. Missing or anonymized rows remain unknown, not measured zero traffic.

### Guided read-only investigation

For device-specific visibility diagnosis, **`gsc-device-movement-review`** guides one read-only `analytics.compare` grouped by `device` over two finalized, equal-length Pacific weeks. It accepts an exact property, optional finalized end date, Search surface and either a URL-section substring (`page_contains`) or property-validated exact landing page (`page_url`), plus either one ISO alpha-3 searcher `country` or bounded `countries` (1-10, e.g. `DEU,AUT,CHE`). Exact-page mode uses Google's case-sensitive page equality in both weeks to exclude sibling URLs. A country list uses Google-side OR filtering within the country dimension and is applied identically in both weeks and any optional drilldown, preserving one combined market scope rather than separate per-country device results. It compares only observed desktop, mobile and tablet rows, never treating absent rows as zero, summing sampled rows into a property total, or inferring mobile indexing faults from a mobile traffic decline. For an exact page, an optional one-period read-only query drilldown retains the same page, device and country scopes; on `webMultimodal` no query drilldown is supported. Discover/Google News have no average-position values. Prompt retrieval makes no Google request; its comparison and at most one optional drilldown consume normal read quota. It never authorizes property or content changes.

An optional exact `query` preserves case-sensitive Google-side query equality in both device periods and any justified page drilldown, with the same page, country and Search surface scope. Alternatively, use `query_contains` (for example `technical seo`) for a case-insensitive topic substring, retained in both device periods and any justified page or query drilldown. Do not combine these selectors. Neither is available for Discover, Google News or `webMultimodal`. When both page and query are exact, the prompt stops after the device comparison rather than broadening either filter or requesting a redundant drilldown.

Call `server.capabilities` to see the names and purposes of all existing guided read-only MCP prompts alongside the tool catalog, even when your client does not display a prompt picker. This is discovery metadata only: using a prompt still requires client support for `prompts/list` and `prompts/get`; listing it does not make an unsupported client able to run it. The catalog itself makes no Google API request, and following a prompt's suggested reads consumes the normal quotas.

New to a Search Console connection? **`gsc-property-readiness-review`** is a read-only MCP prompt that checks credential-state evidence and helps identify accessible exact property identifiers and permission levels using `server.capabilities`, `sites.list`, and an optional exact-property `sites.get`. It never silently chooses another property, changes access, or treats a stored refresh token as verified live Google access. Retrieving the prompt makes no Google request; any subsequently followed Google reads consume normal quota. Its availability depends on the MCP client's prompt support.

**Discover Search-visible pages by surface, topic and market:** `gsc-search-visible-pages-review` guides one bounded, read-only `indexing.list_pages` query for an exact property and optional Web (default), Image, Video, Search News-tab, Discover, Google News or webMultimodal surface, URL section (`page_contains`), supported query topic (`query_contains`), ISO alpha-3 `country` or combined `countries` (1-10), `device` or combined `devices` (1-3), and end date. Combined lists are ORed within a dimension and ANDed with other selected filters in one Google request, **not** separate market/device attribution. Singular/plural conflicts and text-query filters on Discover, Google News and webMultimodal are rejected. Searcher country is not a page's language. The prompt reports observed page metrics and `result_page.has_more` for an opt-in next page, without treating omitted/anonymized rows as zeros or Search visibility as index coverage. Retrieving the prompt makes no provider call; following suggested reads consumes normal quotas. Availability depends on client MCP prompt support.

**Exact-page Search-visible discovery:** Pass `page_url: "https://example.com/de/guide/"` to `indexing.list_pages` or `gsc-search-visible-pages-review` instead of the broader `page_contains` URL section. The full URL must belong to the selected Search Console property. Google applies a case-sensitive `page equals` filter **before pagination**, excluding sibling pages; combining both page selectors is rejected before any provider request. Supported query-topic and country/device filters are preserved in the same single read, with unchanged quotas. An absent result does not prove a page is unindexed or has zero traffic.

**Exact-query Search-visible discovery:** Pass `query: "Technical SEO"` to either workflow instead of `query_contains` to find observed pages for that exact case-sensitive query. Google applies `query equals` before pagination and preserves the selected property, page scope, country/device filters, dates and supported Search surface in the same single read. Combining both query selectors or selecting a text-query filter on Discover, Google News or webMultimodal is rejected before any provider request. Anonymized or omitted rows are not measured zero traffic.

**Custom historical page-discovery windows:** Both `indexing.list_pages` and `gsc-search-visible-pages-review` accept inclusive Pacific `start_date` and `end_date`, for example `2025-06-02` through `2025-06-08` for one campaign week. Both supplied boundaries are retained; omitted boundaries use the tool's existing defaults (a generated end date is capped at the latest complete date). Reversed, invalid and future dates are rejected. Retrieving the prompt makes no provider request.

**Keep page discovery on the same reporting window:** Each `indexing.list_pages` result includes the exact `site_url` and resolved inclusive `start_date` and `end_date`, even when the request omitted dates. If `result_page.has_more` is true, pass `result_page.next_start_row` as `start_row`, both returned dates explicitly, and the same property, surface and filters. Otherwise the default date window can move between requests across a Pacific calendar day boundary. Each continuation consumes the normal read quota; a pinned date range is not a snapshot guarantee or proof of exhaustive Search Analytics coverage.

Investigating a sudden impressions or clicks collapse? Follow the [read-only visibility incident playbook](docs/visibility-incident-investigation.md) to choose the smallest useful sequence of existing daily-onset, traffic-drop, query/page, country and URL Inspection workflows while preserving property scope, finalized dates and quota safeguards. This guide makes no Google API requests by itself and does not claim an SEO cause or recovery.

**Exact-page traffic-drop diagnosis:** `gsc-traffic-drop-triage` also accepts a property-validated absolute `page_url` instead of the broader `page_contains` substring; supplying both is rejected. It guides two adjacent finalized seven-day `analytics.query` date reads with case-sensitive Google-side `page equals` filtering and identical query-topic, country and device scopes (including plural country/device lists). This prevents similarly named sibling URLs from affecting the selected page's evidence. Missing dates remain unknown, not zero. Optional `insights.page_queries` follow-up retains the exact URL and supported scopes; substring-only digest/decay helpers are not substituted. Prompt retrieval does not call Google, while the two suggested reads and any follow-up use existing quotas.

Keep the same finalized end date and all filters; both longer periods must fit within the rolling 16-month history. These are separate periods, not the original seven-day windows. Missing dates and rows remain unknown, not zero; the prompt does not recommend substring-only follow-ups for this mode. Prompt retrieval makes no Google API calls.

Rows with observed clicks and impressions still count when Google omits optional average position: each unavailable `previous_position` or `recent_position` is `null`, and `position_change` is `null` unless both are available. A page may still qualify as likely decay when its click decline is supported by a material impression decline, but missing position never counts as ranking deterioration or improvement. A page appearing in just one returned sample is **not** treated as zero clicks or confirmed decay: Search Console can omit rows, and its API does not guarantee exhaustive page coverage. When `comparable_count` is zero, an empty decay list does **not** establish that the property has no declining pages. This diagnostic adds no Google requests or quota units.

To review only better-supported declines, set `insights.content_decay` `classification_filter: "likely_decay"`. Other values are `weak_insufficient_evidence` and `improving_visibility_with_click_volatility`; omit it or use `all` for the original complete result. Filtering happens **after** both bounded Search Analytics responses and classification, before result pagination: `result_page` reflects the filtered list, while `assessment_count`, `decay_count` and `observed_page_overlap` continue to describe unfiltered observed evidence. It adds no Google requests, cannot recover omitted rows, and does not turn the heuristic into proof of decay.

To focus a large content-decay review on higher-impact changes, set optional `min_click_loss: 20` to return only comparable pages with **at least 20 fewer observed clicks** in the recent period. It accepts nonnegative whole numbers, and `0` or omission preserves every returned decline; `min_click_loss` is echoed as `null` when omitted. Combine it with `classification_filter: "likely_decay"` to prioritize evidence-backed declines of meaningful absolute size. This filters the already returned rows before result pagination and does not alter the original assessment/decay/overlap counts, increase Google's request quota, or imply that omitted Google rows had zero clicks. The observed decline alone does not establish its cause or business impact.

`observed_click_loss` summarizes the number of clicks lost across *returned comparable pages with declines*: `all_declining_pages` includes every observed decline and `likely_decay_pages` includes only the more strongly supported classification. Both remain calculated **before** `classification_filter`, `min_click_loss`, or result pagination, so an analyst can see the observed magnitude without summing every result page. These are not net or property-wide traffic losses, cannot account for missing Google rows or gains on other pages, and do not establish why clicks changed. The summary uses the same two Search Analytics requests.

`observed_click_gain` separately reports positive click changes (`all_gaining_pages`) and the count of pages with increases (`gaining_page_count`) among URLs returned with position data in **both** comparison periods, before local result filtering or pagination. This provides context beside `observed_click_loss` without subtracting gains from declines or presenting a net/property-wide traffic change. Google may omit page rows, unmatched pages are excluded rather than assumed to have zero clicks, and this uses the same two Search Analytics requests.

For `insights.cannibalization`, optional `country` scopes **searcher location** (ISO 3166-1 alpha-3, such as `DEU`) rather than the page language. It combines with `page_contains` and `query_contains` as Google-side AND filters before pagination without additional requests. Impression shares describe only returned pages within that geography/URL scope, not property-wide query shares or proof of harmful cannibalization.

For `insights.cannibalization`, optional `device` selects `desktop`, `mobile`, or `tablet` for investigating overlapping URLs within the same device segment as a weekly digest or quick-wins finding. It combines with `page_contains`, `query_contains`, and `country` as Google-side AND filters before source pagination, without extra requests; omitting it retains all-device behavior. Observed impression shares within a device segment are not property-wide or all-device totals and do not prove harmful cannibalization.

For `insights.cannibalization`, use optional `countries` (1-10 distinct ISO alpha-3 searcher locations) and/or `devices` (1-3 distinct device types) to follow up multi-market quick-win and content-decay findings without narrowing their original scope. Do not supply `country` with `countries` or `device` with `devices`. Search Console applies OR within each list and AND across query, page, country and device scopes in **one** request before pagination. Returned impression shares are for the **combined** observed query/page segment, not independently measured per country/device, property-wide query shares or proof of harmful SEO cannibalization.

For `insights.cannibalization`, optional `search_type` selects `web` (default), `image`, `video` or `news` (Google Search News tab), so a cross-surface quick-wins finding can be followed by a query/page overlap investigation on the same search surface. Omission keeps the original Web request shape; explicit Image/Video/News uses Google's `type` before the same AND filters and source pagination, without additional API calls. Results reflect only observed rows on the selected surface, not all-search or property-wide totals. Discover and the separate Google News service are excluded because they lack query dimensions; multiple URLs alone do not prove harmful cannibalization.

For `insights.cannibalization`, optional `data_state: "all"` includes fresh, possibly preliminary query/page rows when investigating recent URL overlap. Observed impressions and impression shares may change before Google finalizes the data; they are not proof of harmful cannibalization. Omitting `data_state` retains Google's finalized-only request, and explicit `"final"` also requests only finalized rows. Results disclose `data_state` and `preliminary_data_possible`; this option keeps the same single Google request, filters, source pagination, and quota limits.

The `min_page_percentage` threshold is checked against each page's **unrounded observed impression share**; the returned `impression_share` is rounded to one decimal place for readability. A page just below the threshold is not treated as qualifying merely because its displayed share rounds up. These shares are based on returned query/page rows, not unique searches or an exhaustive query-level total.

For `insights.cannibalization` and `gsc-query-overlap-review`, use optional `query` instead of `query_contains` to investigate one case-sensitive query verbatim. Google applies exact query equality before pagination, retaining competing pages within the requested URL section, search surface and searcher segments. The tool echoes the selected query in its structured output; the prompt preserves it in optional follow-ups. No extra requests or quota units are added. The observed overlap is not evidence of harmful competition by itself.

Both `insights.quick_wins` and `insights.cannibalization` echo the exact requested `site_url`, inclusive `start_date`, and inclusive `end_date` in their structured results, so saved opportunity and overlap snapshots can be attributed to the correct Search Console property and time window. These fields are response metadata only; they do not change Google requests, quota accounting, property permissions or filters.

Search Analytics calendar dates (`start_date`, `end_date`, and comparison-period dates) use Google's Pacific Time calendar (`America/Los_Angeles`, UTC-8/UTC-7 depending on daylight saving time), not the caller's local timezone or UTC. This also governs the server's generated/default Search Analytics date ranges.

> **Platform properties.** Search Console now supports platform properties for social/video accounts such as Instagram, TikTok, X, and YouTube in its UI. Google's current Search Console API documentation still defines `siteUrl` using URL-prefix and `sc-domain:` website-property forms and does not publish a platform-property API identifier contract. `sites.list` therefore preserves every identifier Google returns and marks whether it matches the documented API grammar; the other tools deliberately reject undocumented forms instead of inventing an identifier. Use the Search Console UI/export for a platform property until Google documents API support.

Read-write mode requests the Google Search Console read-write and Indexing API scopes. Read-only mode requests only `https://www.googleapis.com/auth/webmasters.readonly` (plus `openid` and `email`) and does not register the six write tools or the read-only `indexing.status` lookup, because that lookup still requires Google's separate Indexing API scope. Read-write remains the default so existing deployments retain their current behavior; see [SETUP.md](SETUP.md) to select a mode before connecting users.

Large analytics responses are bounded at the MCP boundary instead of being generated and then discarded by clients with structured-content limits. List-style tools expose `start_row` / `next_start_row` where applicable; ranked analytical tools expose `limit`, `start_row`, and `result_page` metadata including `has_more`, `truncated`, and `byte_limit_reached`. Continue paging while `has_more` is true rather than assuming one response is complete.

> **Indexing API eligibility and quotas.** Google's Indexing API is not a general-purpose page submission tool — as of this writing, Google's own documentation limits it to two content types: pages with `JobPosting` structured data, and livestream pages with `BroadcastEvent` structured data nested inside `VideoObject`. Before `indexing.request`, the server fetches the target URL and checks static JSON-LD, Microdata, and RDFa markup for one of those two types; if neither is present (or the page can't be fetched), it returns an error explaining why the URL is ineligible instead of calling the Indexing API. Structured data injected only after client-side JavaScript runs cannot be confirmed by this bounded preflight and therefore fails closed. Before `indexing.remove`, the server instead confirms Google's removal precondition: the URL must already return HTTP 404/410 or expose a robots `noindex` meta directive. Update and removal notifications share the same publish quota. Google's current documentation lists a default 200 publish requests/day/project. Its October 16, 2026 update removed an outdated quota request form, but this does not authorize exceeding published quotas or submitting unsupported content. Check your project's API access and current quota in Google Cloud Console. Google also subjects every submission to spam detection and warns that abuse or attempts to exceed quotas through multiple accounts or other means can revoke access. A successful notification is only an acknowledgment that Google received it — it does not guarantee indexing or removal completed.

Weekly digest output includes an exact-property link to the Google Search Console Performance report for quick human investigation. It preserves URL-prefix paths and `sc-domain:` property identifiers. The viewer must have access to that property and manually choose the same date range, search type, and filters as the digest; the link does not set those parameters, grant permissions, or make an additional Google API request.

For a single landing-page client report, use `reports.weekly_digest` (or the guided `gsc-weekly-client-report` prompt) with `page_url: "https://example.com/de/pricing/"` instead of `page_contains`. The full URL must belong to the selected Search Console property. Every aggregate, query and page read uses Google's **case-sensitive page equality** filter; similarly named sibling pages are excluded. Both options are mutually exclusive. Optional `query_contains`, country/device lists and search surface retain their normal Google-side scopes and existing 5-request finalized or 3-request preliminary budget. A matched-period `analytics.compare` follow-up must repeat the exact page equality in both periods; missing returned rows are not measured zero traffic.

Finalized weekly digests now report observed click-through rate (CTR) alongside clicks and impressions, with week-over-week changes expressed in **percentage points**, not relative percentages. Zero-impression periods do not supply a comparable CTR baseline. Preliminary snapshots display only observed current-week CTR without a week-over-week claim. These use already-requested aggregate rows and add no API calls or permission requirements.

The finalized digest links each returned top page directly to its page URL for manual review, retaining short, disambiguated display labels. Recent preliminary snapshots also link their selected page rows and show observed clicks alongside impressions for both selected pages and queries, without asserting week-over-week trends. Only ordinary HTTP(S) URLs become clickable links; malformed or unsafe URL schemes remain escaped plain text. Following a link is the reader's choice and does not make any extra Search Console API request.

Finalized digests also highlight up to three **returned pages with impressions but no observed clicks**, ordered by observed impressions, for follow-up query/page inspection. This uses only the existing up-to-10 current-week page rows and adds no Google API requests. It is not an exhaustive zero-click page audit: Google's top-row selection can omit pages, and absence from this section does not establish that a page had clicks, no impressions, or no opportunity.

Finalized digests separately highlight up to three **returned search queries with impressions but no observed clicks**, excluding diagnostic search-operator queries. Each candidate includes its observed average position when available to help distinguish ranking visibility from potential click-through issues. Average position is not a live Google ranking, and missing position is never reported as position zero. This is limited to the already-requested up-to-25 query rows (which can omit anonymized or lower-ranked queries), with no additional API requests or property-wide claims.

For explicitly recent preliminary digests, a missing aggregate totals row is not treated as zero traffic. Any separately returned page/query samples are still shown as non-exhaustive observations, without fabricated site totals or week-over-week conclusions.

For finalized digests missing either week's aggregate totals, already-returned previous-week query rows can also appear as up to three bounded, non-operator examples. They provide evidence for follow-up investigation even if current aggregate data is absent, **not** proof of lost traffic or zero current clicks. This uses the existing five Search Analytics requests and does not infer a week-over-week trend.

`analytics.compare` also returns `period_comparability`: inclusive calendar-day counts, equal-length status and date overlap. Raw click and impression differences are **not normalized per day**. A separate compact `observed_common_rows_daily_average` summarizes clicks and impressions across only the dimension keys returned in *both* periods, divided by each period's inclusive day count, with an A-minus-B daily-rate difference. These are bounded, matched-row observations, **not property-wide daily totals or a daily time series**; missing keys are never assumed to have zero traffic. Unequal raw window totals are not like-for-like and overlapping dates do not represent independent periods. No additional Google API requests are made.

To investigate more returned keys exclusive to one comparison period without issuing more Search Console requests, use `observed_only_sample_limit: 5` (range 1-10, default 3). Each period's `observed_dimension_overlap` samples remain independently sorted by observed impressions and capped at the requested per-period limit, with `sample_limit` echoed in the result. These are **not** confirmed new or lost queries/pages: Google's row coverage is incomplete and an absent row is not zero traffic. The separate common-key comparison order and pagination do not change.

To prioritize comparable queries or pages from different-length windows, pass `sort_by: "absolute_daily_click_change"` to `analytics.compare`. This ranks returned common keys by the magnitude of the difference between observed clicks per inclusive calendar day, **before** result pagination, without adding per-row payload fields or Google requests. Omit it (or use `"absolute_click_change"`) to preserve the original absolute raw-click-change ranking. This is a sample-scoped ranking, not proof of a property-wide trend; overlapping date ranges remain non-independent.

To surface **relative click growth or loss** among matched queries/pages, set `sort_by: "absolute_click_percentage_change"`. This orders the absolute, unrounded change `(period A clicks - period B clicks) / period B clicks` before pagination. Only rows with **positive observed baseline clicks in period B** qualify: a zero-click baseline cannot be interpreted as an infinite percentage increase, and missing Google rows are never treated as zero. Small baselines can produce large but low-impact percentages, so inspect raw click counts and optionally set `min_impressions_per_period` or `min_baseline_clicks: 20` before acting. The new baseline-click floor keeps keys with at least 20 observed clicks in period B; it also works with other sort modes, defaults to zero, and filters locally before pagination. The relative metric describes raw totals, not daily-normalized rates; unequal or overlapping periods require care. It uses the existing two Search Analytics responses without extra API calls.

To triage only **material observed click movements**, add `min_absolute_click_change: 10` to `analytics.compare`. This keeps common returned queries or pages where the absolute raw A-minus-B click difference is at least ten, whether clicks rose or fell. The default of zero preserves every comparable row. This floor is independent of the selected raw, daily or percentage sort and applies before result pagination; it does not measure daily-normalized impact, infer zeros for missing keys or make additional Google requests. Combine it with `click_change_direction` or `min_baseline_clicks` for more targeted follow-up.

To find observed **visibility changes even where clicks barely move**, use `sort_by: "absolute_impression_change"` (absolute raw impression difference) or `"absolute_daily_impression_change"` (absolute per-day impression difference for unequal windows). These rank only keys returned in both periods, before pagination, using existing data and without extra Google requests. A large impression movement is not evidence of a change in live ranking or a property-wide trend.

For focused triage, pass `click_change_direction: "loss"` or `"gain"` to keep only returned common queries/pages whose clicks decreased or increased. The default `"all"` keeps every comparable key. The direction filter **always refers to clicks**, even when ranking by impressions: either daily `sort_by` option uses per-day clicks, while either raw option uses raw clicks. This distinction matters for unequal windows. Direction filtering happens before result pagination and excludes unchanged keys, while aggregate daily averages still describe all common returned keys before this local filter. It does not request additional Google data or imply that missing keys have zero traffic.

For visibility triage, `impression_change_direction: "loss"` or `"gain"` filters common returned queries/pages by observed impression movement, independent of clicks (default: `"all"`). Either daily `sort_by` option compares impressions per calendar day; either raw option compares raw totals, so unequal windows may reverse the direction. Impression and click direction filters can be combined (both must match), operate before pagination, exclude ties and leave common-row daily averages unfiltered. These are local comparisons of returned data, not evidence of changed live rankings or zero traffic for missing rows, and require no extra Google API requests.

For observed click-through movement, set `sort_by: "absolute_ctr_change"` to rank common returned keys by absolute CTR percentage-point change, calculated from **unrounded period CTR fractions** even though the displayed `diff.ctr` is rounded. This mode excludes rows with zero observed impressions in either period. Optionally set `min_impressions_per_period: 100` to include only keys with at least 100 returned impressions in **each** period, before ranking and pagination; the default is zero and other sort modes remain unchanged. The filter is local and does not add Search Analytics requests. CTR movement is not evidence of changed live rankings or a statistically significant trend; these are bounded returned rows, not the full property.

To inspect CTR declines separately from improvements, add `ctr_change_direction: "loss"` or `"gain"` (default: `"all"`). This compares **unrounded CTR fractions** for keys returned in both periods and with positive impressions in each; zero-impression baselines and unchanged CTR are excluded from either directional result. It works with any `sort_by`, alongside existing click/impression direction filters and `min_impressions_per_period`, before pagination. The direction is CTR-specific even for daily click or impression ranking; no additional Google requests are made. Filtered observations are not statistically significant by themselves, and missing rows are not zero.

To inspect observed changes in **average Search Console position**, use `sort_by: "absolute_position_change"` with `analytics.compare`. This ranks matched returned keys by the absolute difference between **unrounded** period-average positions, before pagination, requiring an actual position and positive impressions in each period. It works with `min_impressions_per_period` and the independent click, impression and CTR direction filters; other defaults remain unchanged. Discover and Google News have no average position, so this sort is rejected for those surfaces. Lower average positions are generally better, but changes in averaged positions are **not a live ranking**, a unique URL rank, or proof of SEO impact. The sample is bounded to Google-returned rows and no additional Google API calls are made.

To review **average-position improvements separately from declines**, set `position_change_direction: "improvement"` or `"decline"` (default: `"all"`). Compared with period B, a **lower** period A average position counts as improvement, a **higher** one as decline. Filtering uses unrounded average positions for returned common keys with positive impressions and available positions in both periods, excludes ties, and applies before pagination with any ranking mode and impression floor. Discover and Google News reject a directional position filter before Google requests. Average-position movement is not evidence of a specific live URL ranking change, and no additional provider requests are made.

MCP clients can call read-only `server.capabilities` to discover the existing `analytics.compare` `sort_by`, click/impression/CTR/position direction filters, `min_baseline_clicks`, `min_absolute_click_change`, and `min_impressions_per_period` before selecting a reporting workflow. Its description covers returned common rows only; it does not imply complete Search Console coverage or a live ranking change.

## What you can ask

For a multilingual site, call `indexing.list_pages` with `page_contains: "/de/"` to find Search-visible pages within the German URL section. To distinguish visitors in Germany on mobile from visitors elsewhere, add `country: "DEU"` and `device: "mobile"`; searcher country is not page language. For a combined market/device segment in **one** Google read, use `countries: ["DEU", "AUT"]` and `devices: ["desktop", "mobile"]` instead of the singular fields. Lists are ORed within each dimension and ANDed with the other selected filters, not separate country/device reports; duplicate entries and mixed singular/plural selectors are rejected. Optional `query_contains: "seo audit"` narrows supported Search surfaces to observed topic traffic. The filters run at Google before pagination and add no API requests. The response echoes selected scopes, and its metrics describe only matching Search Analytics rows, not property-wide traffic. Omitting optional filters preserves the unfiltered behavior. This is not a complete index-coverage inventory: use URL Inspection to check an individual page's indexed state.

For page discovery on a different Search surface, pass `search_type: "image"`, `"video"`, `"news"` (the Search News tab), `"discover"`, `"googleNews"` (the News app/site), or `"webMultimodal"` (Lens, Circle to Search and image uploads). Web remains the default; the `search_type` response field is omitted for default Web requests. A selected non-Web surface is returned as `search_type`; its page metrics are **only for that surface**, not total Web or all-channel traffic. Text-query `query_contains` is unsupported for webMultimodal, Discover and Google News and is rejected before provider/quota work. For these surfaces, use page URL sections, searcher country/device and observed clicks/impressions without inventing query text or average position (which can be `null`). This choice changes the scope of the existing one-request read, not the number of Google calls; no Search-visible row proves index coverage.

**Agency reporting workflow:** [Read-only weekly Search Console reporting for SEO agencies](docs/agency-weekly-reporting.md) walks through exact-property verification, one bounded weekly digest, matched-period comparisons, evidence checks, and a reusable human-reviewed client report. It contains no fabricated client metrics or automated outreach.

Weekly digest headings retain the URL path for a URL-prefix property (for example, `example.com/de/` versus `example.com/fr/`) so reports for different site sections remain distinguishable. HTTP URL-prefix headings explicitly retain `http://` to distinguish them from HTTPS properties; Domain property headings identify their broader property type. Common HTTPS root properties keep short host headings. This reflects Search Console's separate protocol/property scopes, not guaranteed complete traffic.

For a `sc-domain:` property, weekly digest top-page labels retain the complete observed URL (including host and protocol), even when only one matching path appears in the top-five sample. This avoids misattributing a page to the wrong subdomain; URL-prefix reports still use compact page paths when unambiguous. These are sampled Search Analytics rows, not a complete inventory of pages.

Finalized weekly digests now report the distinct query rows observed in each bounded week and how many appeared in both. When neither week supplies a matching returned query, stable site-level totals are **not** presented as evidence of stable query-level performance. These counts use the same up-to-25 query rows already fetched per period, without extra Google requests, and do not establish exhaustive query coverage.

The digest also lists up to three non-operator queries returned this week but absent from the previous week's bounded query sample, ranked by their **observed impressions**. These are inspection examples, not verified new searches or rankings: an unreturned query is not a measured zero, and anonymized queries may be missing. This reuses the existing five finalized Search Analytics requests without consuming more Google quota.

Finalized digests also show up to three non-operator queries observed only in the **previous** week's returned sample, ranked by previous impressions. These are follow-up investigation prompts, not proof of lost traffic or ranking declines: missing current rows are not measured zero. The same five bounded requests are reused.

Once connected, ask your assistant things like:

- *"What are my top 20 queries by clicks in the last 28 days?"*
- *"Compare impressions for example.com this month vs last month — which pages dropped?"*
- *"What does Google's indexed version of `https://example.com/pricing` show for index status and last crawl?"*
- *"Which high-impression query/page rows have an average position between 5 and 15? Show me those optimization opportunities."*
- *"Give me a weekly digest for `sc-domain:example.com` ending today."*
- *"Do any of my sitemaps have errors or warnings?"*
- *"Using this brand regex I provide, approximate my clicks as brand vs non-brand."*
- *"How is my site doing in Google Discover vs regular web search?"*

Query regexes are a manual approximation only. Google's native `brandedClassification` on the Search Analytics API uses AI-assisted classification (including variants and related products). `analytics.query` can group by this dimension or filter with `dimension: "brandedClassification", operator: "equals", expression: "BRANDED"` (or `"NON_BRANDED"`). `analytics.compare` accepts the same native filter for both periods. Do not combine native branded classification with a query filter. It is available from February 21, 2026 for eligible top-level properties with sufficient traffic only; no returned classification rows does **not** prove zero branded or non-branded traffic.

For a guided, read-only comparison across two matched weeks, use the discoverable `gsc-brand-traffic-review` MCP prompt. It calculates both explicit inclusive seven-day Pacific windows, defaulting to a usually finalized end date three Pacific days ago and rejecting explicitly newer, nonfinal dates. Optionally pass `page_url` for **one property-validated exact landing page** (Google-side case-sensitive page equality, excluding sibling URLs), or `page_contains` (e.g., `/de/`) for a URL section within the **same eligible top-level property**; the two selectors cannot be combined. String-valued `countries` (e.g., `DEU,AUT,CHE`) and `devices` (e.g., `mobile,desktop`) focus one combined regional/device segment using Google's `filterLists` in **both** periods. These list arguments accept comma/newline-separated text or a JSON-array string, not a raw JSON array over MCP. The exact-page or URL-section, country and device filters are applied together at Google to both periods; the results are segment-only, not site totals. It queries Google's native branded classification in the selected Search surface, reports only categories actually returned, and keeps unavailable classification distinct from measured zero traffic. `query` filters are not compatible with native branded classification. Retrieving the prompt itself does not contact Google or send a report.

Search Console also has dedicated Generative AI performance reports for Search and Discover. The current documented Search Analytics API does not expose a dedicated Generative AI search type or filter selector, so this MCP does not guess one. AI Overviews and AI Mode remain included in overall web Search performance data; use the Search Console UI for the dedicated Generative AI report until Google documents API access.

Google documented the `webMultimodal` Search Analytics API search type on November 16, 2026. Use `search_type: "webMultimodal"` with `analytics.query` or `analytics.compare` to inspect Google Lens, Circle to Search, and image-upload performance on its own surface, separate from ordinary Web Search. Because these searches are image-led, the text `query` dimension and filters are unavailable: choose page, country, device, date, or aggregate `dimensions: []` in `analytics.query`, and page/country/device for comparisons. `search_type: "multimodal"` is not a valid substitute, and a guessed `searchAppearance` value is not equivalent. Google may omit rows; do not infer zero traffic or sum across surfaces as if they are mutually exclusive.

To review that surface without manually assembling an analysis, use the discoverable `gsc-visual-search-review` MCP prompt with an exact `site_url` and optional `end_date`, `page_contains` (URL section) **or** property-validated `page_url` (one exact landing page), `countries` (ISO alpha-3) or `devices`. Exact-page filtering uses Google's case-sensitive page equality and excludes similarly named sibling URLs; it cannot be combined with `page_contains`. Supply optional country/device lists as comma/newline-separated strings (or JSON-array strings) as with `gsc-brand-traffic-review`. It calculates two explicit, adjacent finalized Pacific weeks, rejecting an explicitly nonfinal end date instead of comparing preliminary days as settled. It guides two `analytics.query` aggregate reads and, only for non-exact-page scopes, optionally one `analytics.compare` landing-page read with the same Google-side filters. If a longer-window landing-page decline would change the decision, it can optionally guide `insights.content_decay` over 28 days on the same visual-search surface and page/searcher scope, without unsupported text-query filtering; this is a separate comparison with its own read-quota cost. The guidance does not infer zero traffic from missing rows or present filtered samples as site totals. Getting the prompt makes no Google request; following it consumes normal read quotas and never authorizes publication or indexing changes.

## Compare observed landing-page cohorts

**`gsc-page-cohort-review`** is an MCP-discoverable, read-only workflow for examining which *observed top canonical page URLs* changed between two adjacent finalized seven-day Search Console windows. It accepts an exact property, optional end date, one Search surface (including `discover`, `googleNews` and Google Lens `webMultimodal`), URL-section substring, either an optional case-sensitive exact `query` (up to 240 characters) or `query_contains` search topic (up to 120 characters), and single or multi-value country/device scopes. Country/device lists (1-10 countries, 1-3 devices) use Google-side `filterLists` identically in both windows. Query equality or topic substring is applied at Google to both periods, not filtered locally; resulting page cohorts are query-segment samples, not property-wide totals. A page URL section is not a searcher locale. Compare only pages returned in both click-sorted, incomplete samples: a page absent from one week is **not measured zero traffic** or confirmed deindexed. Optionally inspect one page's query context when supported, preserving all filters; skip this redundant query-grouped drilldown when an exact query is already selected. Discover, Google News and the multimodal surface have neither query filtering nor query-dimension drilldown, so both query selectors are rejected there. Discover and Google News comparisons have no average position; report clicks, impressions and CTR without inventing ranks. Google News is distinct from the Google Search News tab (`news`); do not combine surfaces or silently broaden filters. Retrieving this prompt consumes no Google requests; following it uses ordinary read quotas. No indexing, content, publication or other writes occur, and client prompt support varies.
